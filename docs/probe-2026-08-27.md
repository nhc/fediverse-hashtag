# Capability probe, 27 August 2026

Everything in this file was measured, not assumed. The probe made a handful of
unauthenticated requests to public endpoints on ten servers, identifying itself
in the User-Agent. Re-run it before trusting any of these numbers again, because
instance configuration changes without notice.

## The five findings that shaped the design

**1. Public hashtag timelines are not universally public.**
`infosec.exchange` returns `422 {"error":"This method requires an authenticated
user"}`. That is the `DISALLOW_UNAUTHENTICATED_API_ACCESS` setting, and any
instance can turn it on at any time. Capability has to be probed per instance and
re-probed on a schedule. It cannot be inferred from software version.

**2. Tag metadata survives where timelines do not.**
`/api/v1/tags/:id` returned 200 with seven days of history on all nine Mastodon
hosts, including the one that blocks timelines. The history is daily granularity
only, and it carries a distinct `accounts` count as well as `uses`:

```
{'day': '1787788800', 'accounts': '58',  'uses': '84'}
{'day': '1787702400', 'accounts': '107', 'uses': '161'}
```

This is a cheap, widely available, corroborating signal. It cannot support a
five-minute window, but it is useful for cold tags and for sanity-checking the
index against what an instance believes about itself.

**3. `any[]` batching works.**
One request to `/api/v1/timelines/tag/cats?any[]=dogs&any[]=birds&limit=40`
returned 40 statuses covering all three tags: 22 cats, 9 dogs, 9 birds. This
matters, because request budget is the scarcest resource in the whole system.

The catch is that `limit=40` is shared across the batch. A busy tag will crowd
out a quiet one. Batching is therefore only safe for tags of similar volume, and
never appropriate for the busiest tags.

**4. Incremental polling works properly.**
`limit` caps at 40, whatever larger value is requested. The response carries a
`Link` header with both `next` (a `max_id`) and `prev` (a `min_id`):

```
link: <...?limit=2&max_id=117168011495507211>; rel="next",
      <...?limit=2&min_id=117168066166883357>; rel="prev"
```

Passing `min_id` set to the newest previously seen id returned zero statuses when
nothing new had arrived. So a cursor per instance and tag pair gives clean
incremental collection with no repeated payload. The ids are instance-local
snowflakes, so the cursor cannot be shared between instances.

**4a. `min_id` paginates forward, not backward.**
This one matters, because getting it wrong loses posts silently. Taking the
oldest of a 40-status window as a cursor and then asking for only five returned
the five statuses immediately *after* that cursor, not the five newest overall:

```
baseline window: 40 statuses, positions 0 (newest) to 39 (oldest)
min_id=<position 39> limit=5  ->  positions 34, 35, 36, 37, 38
```

So `min_id` anchors the page at the older end and works forward. Two consequences.
Advancing the cursor to the newest id in the response is safe and skips nothing.
And a response that comes back full means there is a backlog rather than a loss,
so the cursor carries a `behind` flag and is polled again on the next tick
instead of waiting out its tier interval.

The `rel="prev"` link is exactly the next cursor, so it is used in preference to
deriving one from the statuses.

**5. Overlap is high, but the union is genuinely larger.**
Fetching the same tag from three instances at the same moment:

```
mastodon.social = 40   hachyderm.io = 40   mstdn.social = 40
social ∩ hachyderm = 31      social ∩ mstdn = 34
union of all three = 50      (against 40 from any one alone)
```

Twenty-five per cent more unique posts from three instances than from one. The
returns diminish quickly, but they are real, and the overlap is not waste. It is
the measurement of coverage. A post seen by seven of eight instances sits in the
well-connected middle of the network. A post seen by one sits at the edge, and
tells the index where its vision stops.

## Two incidental findings worth keeping

**Federation delivers some non-Mastodon coverage for free.** Origin hosts in a
single mastodon.social tag timeline included `piaille.fr`, `eldritch.cafe`,
`lgbtqia.space`, `c.im` and `pixelfed.social`. Pixelfed's own API refused the
probe, yet Pixelfed posts arrive anyway through federation. Coverage of other
platforms starts above zero without any adapter being written.

**Hashtag timelines appear to carry originals only.** A sample of 40 statuses
contained no boosts at all. Boosts do not carry the tags of the post they
promote, so a tag timeline is an originals feed. Separating originals from boosts
is therefore mostly answered by the endpoint choice. Reblog counts are available
per status as a separate and partial signal.

## Rate limits, as reported

Every Mastodon host returned the same headers:

```
x-ratelimit-limit: 300
x-ratelimit-remaining: 299
x-ratelimit-reset: 2026-08-27T15:00:00Z
```

Three hundred requests per five minutes, per IP, resetting on the five-minute
boundary. That is sixty requests a minute per instance, which is far more than
this index should ever use.

One caveat that the probe could not test from a laptop. That limit is per IP, and
a Worker egresses from shared Cloudflare addresses. The index may end up sharing
a bucket with unrelated traffic, and some instances throttle or block datacentre
ranges outright. This needs verifying from a deployed Worker before the instance
list is finalised.
